# Review protocol

Return a verdict, a short reason, the validation run, and findings ordered by severity, in the shape defined in `references/review-output.md`. APPROVE needs sufficient evidence and no credible blocker; REQUEST_CHANGES needs a supported blocking defect; uncertainty is a question or COMMENT. Self-review uses COMMENT unless policy and explicit authorization permit self-approval. Report a reviewer model only from trusted runtime metadata, else `unknown`; a delegated reviewer reports its own model.

The agent owns the review-fix-validate-deliver loop. A single pass both under-finds and over-holds, so for a consequential change take a second context-isolated pass by default — not only when one is requested. Give the second reviewer the diff plus the first pass's findings and task it with two jobs, not one: refute the standing findings and surface what the first pass missed. Refutation comes first — false positives are now the dominant failure mode of automated review, so any standing finding whose support cannot be re-grounded against the actual code is dropped, not kept. The second reviewer removes findings as readily as it adds them. Prefer a fresh reviewer from a different model family when available and authorized, given intent, diff, context, and validation but not the prior verdict; disclose any fallback. Allow three repair rounds plus one clean review unless told otherwise; stop on convergence or the same finding surviving two repairs. Re-review after edits — an earlier clean review cannot certify later ones. A remote-readiness claim needs the remote head to match the reviewed candidate with required CI green. Do not post reviews, replies, or resolutions automatically; use authorized delivery.
